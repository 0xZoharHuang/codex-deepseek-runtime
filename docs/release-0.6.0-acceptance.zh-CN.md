## 新发现与补充验收

完整 Linux 回归中的图片失败暴露了进程身份风险：旧实现以可受时钟变化影响的 epoch 时间识别 owner。确定性复现表明，同一 PID 和内核启动标识不变时，仅旧时间观察偏移就可能误清理仍在使用的图片锁。新实现复用已有的内核进程身份接口，无法确定存活时保留锁，并以账本版本区分新旧记录；不会据此自动重放请求。原完整运行并未记录同时刻的时钟变化，因此不把该复现当作已证实的原始触发条件。另一项失败是 POSIX 测试错误要求私有目录中新文件必为 0600，现按实际目录遍历权限验证。

原生接口对照已经在此前 Windows 候选上完成：对应官方与候选导出的 456 份定义一致。实际故障注入包含截断 SSE、TCP 中断、401/403、工具执行前后断流、worker 退出和冷恢复，共 14 个官方/候选对照场景通过；副作用次数与原生重试路径一致，没有另建去重或自动重放器。401/403 的默认六次请求也另用官方运行时直连基线确认，随后显式修复测试凭据才恢复。最初证明绑定 da69400d47674c6660f0；f3699ef1f89574698b2b 已重跑 14 个故障场景、MCP 生命周期与账户边界并通过。新 Windows 原生包仍须重新绑定和实测。

补充复杂任务使用 [Terminal-Bench 的 mvcc-lsm-compaction 固定原题](https://github.com/harbor-framework/terminal-bench/tree/452bf305c6daa62fc59061d22133a7cbc7c1572e/tasks/mvcc-lsm-compaction)。原工程独立测试为 12 项失败、3 项通过。实际 Linux f3699ef1f89574698b2b / 原生包 3fe874… 中，DeepSeek 自行修改 4 个源码文件，经 20 次原生命令与 6 次文件变更事件完成修复；23 个真实模型请求全部由显式固定的官方 DeepSeek 提供方完成。独立未修改 oracle 的最终结果为 **15 项通过，0 失败、0 跳过**，覆盖多版本时间线、交错写入、变异和空间限制，不能仅保留所有历史版本蒙混过关。

模型环境已通过原生命令、文件接口及进程路径验证不能读取参考答案、测试控制器及 Windows 挂载中的副本。控制器没有代写业务代码。原始编译、复现与 sanitizer 失败记录均保留；完成后相关进程自然退出，独立 oracle 未改动模型完成的 14 个工程文件。该任务没有使用子智能体，因此不作为协作机制证据；它是固定工程的实际独立验证，不是官方 Harbor/Docker 成绩或排行榜结果。后续 Windows 专属修改不能改写本次运行实际绑定的源码身份。

## 原生机制及平台边界

原生基线固定为 Codex `0.164.0-alpha.7`，提交 `fe136d4e70ef2b5bbed40a2d22b3aabf267796d3`。已实际比较对应官方与此前 Windows 原生候选导出的 456 份实验接口定义，内容一致；新 Windows 原生包必须重新导出核对并绑定最终安装及完整运行结果。

Windows 剩余本地方法已有 59 项正向效果、1 项经官方对照的平台边界及 4 项后端边界的证据。R7 补充控制器遗漏官方对照证明的环境绑定，导致该次平台边界断言失败；原始失败保留，R8 控制器已补充显式校验，仍待实际复测。固定原生 Windows restricted-token sandbox 不支持 legacy `command/exec` 的部分流式控制路径；官方与候选返回同样的明确错误，报告不将其写成成功执行。受支持的统一命令、后台控制、权限拒绝和终止仍分别验证。

Guardian 验收区分同步审批实际依据与稍后发布的 V2 评分：按获批的实际命令 ID 和动作绑定；外层请求完成却没有发布评分时保留该事实及原因未知，不能推断成功评分。独立真实 MCP 验证还观察到已发布的低风险 V2 分数被原生缓存路径采用，且第二次工具执行没有人工回调或新的同步审核请求；官方 OTLP 指标与工具效果对应。最终安装仍须重跑标准 Guardian 验收，包括旧断言失败后未到达的中断检查。
