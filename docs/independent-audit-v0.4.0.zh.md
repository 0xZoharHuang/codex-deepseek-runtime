# v0.4.0 独立审计与 v0.4.1 修正

本次从公开的 v0.4.0 提交 `461e77c1dda5af300f0922b6e142c66989ac7d26` 重新检查源码、验收谓词和私有原始证据。验收对象是 Codex CLI 的本地 runtime：任务循环、工具调度、沙箱和审批、持久会话、MCP、子智能体、后台任务等。模型判断水平和服务端账号权益不作为 runtime 等价的条件。

最终是否通过，以本版本的 `reports/acceptance.json` 和 `reports/independent-audit-v0.4.1.json` 为准。开发候选、失败场景和被替代的验收快照均单独保存；不会因后来通过而改写原来的失败结果。

## 实际修复

| 问题 | v0.4.0 的行为 | 修正与验证 |
|---|---|---|
| 结构化输出只检查最后一条消息 | 前置无效最终消息可被后面的有效 JSON 掩盖 | 检查每一条最终消息；流式和非流式反例均纳入测试 |
| 响应含工具调用时整段跳过 schema 检查 | 显式 `final_answer` 也会被跳过 | 保留原生工具说明语义，仍检查显式最终答案 |
| 错误最终消息延迟到响应终点才检查 | 后续工具完成事件可能先被放行 | 在显式最终消息完成时立即校验；原生故障注入验证无客户端工具执行 |
| 极大指数被 Python 解析成非有限数 | `1e999` 可通过普通 number 类型检查 | 拒绝非有限数，进入原生错误与重试路径 |
| 单页比整个网页缓存预算更大 | 返回的引用可能已经被立即淘汰 | 写入前明确报错，保留既有页面；限制链接元数据和行数展开 |
| 环境变量隔离过滤过宽 | 原生 TUI 会话记录、终端兼容选项和 rollout trace 等开关被清掉 | 保留经源码核对的原生选项，检查诊断输出路径不与 App 状态重叠；真实 PTY 和冷恢复验证原生记录文件 |
| 网页场景只检查网络访问和文件结果 | 模型跳过 `find` 仍可能通过 | 强制从原生事件核对 `open → 正向 find → click` 的引用、链接和先后关系；实际拦住两次遗漏 `find` 的执行 |
| 子智能体投递使用字符串包含判断 | 任务描述中的字样可能被误算作结果 | 识别正确子智能体发来的 `FINAL_ANSWER` 载荷；原始 v0.4.0 证据经更严格谓词复核仍通过 |
| Code Mode 与用户输入的场景谓词过宽 | 普通命令效果或其他回调可能被误算成对应机制成功 | 核对实际成功的原生 Code Mode 调用及结果；用户输入须有本轮、本线程的真实提问回调 |
| 真实任务浏览可由历史或其他线程满足 | 旧候选、先前轮次或 reviewer 的操作可能混入当前验收 | 最终续做轮次必须由父线程亲自完成成功的网页操作和正向查找 |
| 工作补丁仅使用普通 `git diff` | 已暂存改动和新建、未跟踪的回归文件可能缺失 | 捕获相对 HEAD 的全部改动和未跟踪文件；以二进制文件重放验证，保持 Git index 不变 |
| 验收汇总过度依赖布尔字段 | 方法集合、原始行或 verifier 身份可能未重新比对 | 核对准确方法集合、逐项原始结果、verifier 哈希和当前安装；从 JUnit 统计实际通过数 |
| 测试凭据清理不完整 | Secrets 模式的临时 home 加密 key 可能遗留 | 仅删除已关闭测试 home 对应的精确 Keychain 账户，并回查不存在；保留 App 和 OpenRouter 凭据 |

结构化文本校验与工具执行分别处理，符合[官方 Structured Outputs 的用途划分](https://developers.openai.com/api/docs/guides/structured-outputs)。适配器不清洗错误答案来伪造通过，不执行工具，不增加模型重试循环；报错后仍由原生 Codex 决定如何继续。

## 没有重造 runtime 的关键业务

本轮没有新增原生 Rust 补丁。现有补丁在固定上游 `fe136d4e70ef2b5bbed40a2d22b3aabf267796d3` 上独立重放，结果与已交付源码哈希一致，外部 Cargo 依赖不变。另行核对的 348 个任务、调度、工具处理和沙箱相关文件保持上游内容。

```text
用户任务
   |
   v
原生 Codex CLI runtime
   |-- 原生任务循环、队列、持久会话和恢复
   |-- 原生工具调度、执行、审批、沙箱
   |-- 原生子智能体、Hooks、Skills、MCP 客户端
   |
   |-- 模型请求 --> Responses 协议适配和原生 HTTP 传输 --> OpenRouter / DeepSeek
   |                    只转换协议、校验结果和维护连接
   |
   `-- MCP 调用 --> codex_web 文档读取器 --> 真实网页
                        只负责文档 I/O 与解析
```

现有原生接入补丁的两处选择条件也须明确披露：`core/src/tools/spec_plan.rs` 调整固定模型在选择 v2 时的后代工具可见性；Guardian 修改辅助分类器的模型选择。这两处没有实现新的调度、工具 handler 或审批算法。其余接入修改覆盖 provider 绑定、独立凭据命名空间、HTTP 网络策略以及 Unix socket 的 WebSocket framing。

## 证据复核和真实工程

旧私有证据归档重新逐文件校验，并确认公开报告引用的 18 份收据都在归档中。原生源码归档的 regular/hardlink 内容也全部重新核验。新安装重新生成 456 份公开 schema，与同版本官方二进制比较。

本次没有沿用旧矩阵的“已观测”标记来证明新版本：`verify_rpc_observations.py` 从当前验收的客户端请求和原生响应重新配对，再与 125 个本地方法集合对照。RPC 成功记录与实际状态、文件、网络、生命周期等后置条件是两层证据，须共同满足。

Jinja 和 HTTPcore 都从修复前的固定真实源码开始，先验证基线和独立 oracle，再由隔离的原生 Codex + DeepSeek 修复、运行完整测试并取得原生子智能体审阅。HTTPcore 在编辑后有意中断并冷恢复；第一次提交虽然通过完整单测，独立真实 TCP 压力仍发现连接所有权竞态，因此原结果保留为失败，再通过同一保存任务提供原始反馈继续修复。最终检查包括多次真实 TCP 压力、asyncio/Trio 取消、TLS 对端 EOF、完整套件、独立 oracle、当前轮次的真实网页操作和新一轮审阅。

所有测试 home、会话、provider、Keychain 测试条目和入口与 Codex App 分离。已结束阶段的原始证据在校验压缩副本后才清理展开目录；活动任务和已发布版本不作为临时缓存删除。
