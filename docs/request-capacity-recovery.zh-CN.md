# 请求字节容量与旧会话恢复

**现行发行证据见 v0.7.2。** 固定 Windows P41 发布版已用真实 16 图任务补验显式原生压缩及同会话冷恢复，实际任务的请求均返回 HTTP 200。自动 413 路径、旧 CP6 和其他平台保留各自的版本及回执范围。[v0.7.2 发布版实测](../reports/releases/0.7.2/README.md#windows-发布版长图片补验)

下方保留历史 P29 原生控制实验。Linux exact44 当时覆盖原 33 项和 11 项 token／真实 writer 提交用例。每份历史记录只归属于原测试产物和环境。[历史候选验收矩阵](candidate-acceptance.zh-CN.md)

## 为什么有图的会话会卡在 413

HTTP 413 表示请求字节容量被拒绝。图片、工具历史和文本都影响请求大小，token 估算不能替代字节检查；它与真正的上下文窗口超限（CWE）是两种错误。实现保留原始 413，不伪装成 CWE，也不靠删掉待处理图片或工具结果来制造成功。

这些改动仍使用原生 Codex 的压缩、上下文安装、工具与会话机制，没有另写 agent loop、工具调度或子智能体系统。

## 如何保留还没处理的内容

```text
发送时的原生历史
    [此前已确认消费的前缀 | 尚未确认消费的完整后缀]
                 |
       明确的响应开始前 413
                 |
       原生压缩 / 显式 TokenBudget 本地重置
                 |
    [新上下文             | 完整保留的原始后缀]
```

普通模型响应真正 `Completed` 后，才记录它实际发送并消费的前缀，推进普通完成序号（epoch）。工具已执行、请求已发出、压缩生成了摘要，都不等于新的普通响应已消费输入。自动恢复只可使用已经确认的前缀，并限制同一 turn、同一确认 epoch 的重复恢复；半截流和结果未知不能当作这种前置拒绝。

自动容量恢复复用原生本地压缩。当前候选先固定一个可证明归属的历史目标；若单次请求仍遇字节容量或真正 CWE 限制，按连续且工具配对安全的边界分块，每个后续请求携带上一次真正成功的新摘要。只有新摘要的完整覆盖链读完该捕获目标后，才安装一次替换；不能用一个小请求成功冒充整个目标完成。当前 turn、并发追加及归属不明的后缀保持原条目、顺序、图片和调用/结果 ID。旧 CP6 游标本身不能授权丢弃游标后的历史。

旧会话可能没有这份确认记录。显式手动压缩会要求**本次请求新生成的非空摘要**；整个输入遇到 413 或真正 CWE 时，按安全的历史条目边界缩小为严格前缀，保留工具调用与结果配对。摘要替换该次成功提交的前缀，其余完整后缀继续保留。原生通知会报告 `N/M`：此次覆盖的历史条目数 / 捕获的总条目数，不能把它解释成所有内容都压缩完成。旧摘要不能冒充本次成功；不可再缩小时保留原始失败。

`TokenBudget` 仍须显式启用。已确认游标足以覆盖可重置前缀时，使用原生本地上下文重置、生命周期和 hooks，不发摘要模型请求或伪造摘要响应 ID。若旧游标之后还有必须读取的历史，则先经本次新摘要覆盖该历史，不能借 TokenBudget 重置未确认内容；功能本身仍保持启用。413 不会偷偷开启 TokenBudget，普通原生重置路径也没有被另一套业务循环取代。

冷恢复校验沿用原生 rollout 的反序列化语义。只有校验哈希的临时投影会排除原生读取时忽略的 `cell_id`、`executed_tool_calls`、`tool_calls_complete` 三项执行元数据；历史条目、模型输入和发送内容不会因此改写。内容、顺序、会话或模型绑定不一致时，不把旧记录当作可用的确认凭据。

## 怎样确认压缩真的结束

使用原生 app-server 的客户端，应先完成 `initialize` / `initialized`，在原有独立 home 中恢复目标线程，再调用 `thread/compact/start`。接口仍只接受原生参数；不要自行添加保留图片数等参数。

1. 保存请求 ID，核对对应 RPC 响应。收到 `{}` 只代表命令已接受。
2. 跟踪目标线程的压缩 turn，核对同一个 `contextCompaction` item 的开始、完成及其 item ID、turn ID；同时保留该 turn 的警告和错误。
3. 等待同一个 turn 的 `turn/completed`，核实完成状态。失败、取消或连接中断不能按成功处理；`N/M` 警告仍表示只完成了部分历史压缩。
4. 下一条普通 turn 真正完成，才证明其余待处理输入继续得到消费；不能用另一个线程或 turn 的成功代替。

## 取消与检查点提交

官方 fe136 的外层任务控制器在取消 token 后保留最多 100 ms 的 grace，再中止原任务并发出 `TurnAborted`。取消请求之后、native `TurnAborted`/ACK 之前出现 `Compacted`，本身可以是上游行为；上游没有承诺“请求一发出就绝不安装”。CDS P28/P29 的该控制器文件逐字相同，SHA256 为 `f60826f32040ac7f95a5cf351767d58fe3fb7cfc09c90c873bba484b175cfc44`。

P29 将现有原生 token 传入容量扩展使用的共用本地压缩路径，在最后状态锁检查之前更保守地停止；普通本地压缩也会更早响应这个 token。这是容量扩展的行为细化，不是恢复一个上游本来存在的保证。窗口推进与历史替换经过同一次检查；一旦已被接受的替换发生，就由原有 native persistence tracker 和顺序边界完成 rollout ACK、检查点 CAS 和内存发布。父任务被中止不会通过丢弃 awaiter 放弃这段已接受的提交，后续普通输入也不能越过它；实际 I/O 失败仍保留错误和检查点不可用状态，不保证跨文件回滚。已经被接受的持久化可能继续收尾，不能把它解释成又启动一轮模型或工具工作。

这保护的是已确认前缀、response/epoch、所有权及 attempt fence 的一致性；不宣称多个文件在断电下构成数据库事务。原生非容量路径的 summary output、hooks、remote compaction、普通 TokenBudget 和外层任务生命周期保留各自原有语义，没有新增 agent loop 或 scheduler。

## 删除与后台写入的边界

原生线程删除只等待关闭一段有限时间，已经获准的后台写入可能晚到。修复没有延长原生业务删除，也没有另建线程管理器，而是在原有每线程锁文件中保留固定 26 字节删除标记：

```text
后台写入 --> 取得原有锁 --> 检查删除标记 --> 允许时才发布检查点
线程删除 --> 取得同一锁 --> 同步删除标记 --> 移除检查点
```

先写完再删除，检查点会被移除；先删除再写，晚到写入会被拒绝。即使原来还没有缓存目录，也先建立该线程的删除标记。带删除标记的残留检查点不能用于冷恢复；不同 home 或线程 UUID 不受影响。锁不保存历史或凭据。标记同步与原生业务删除不是跨文件事务，也不声明断电情况下的原子性。

[71 项选定原生核心回归报告](../reports/payload-capacity/native-core71-20261025.json)包含 22 项检查点、41 项压缩、6 项工具配对与 2 项关闭等待用例，逐名执行各一次且没有忽略项。新增删除边界的 6 项预检另行记录，没有重复计入 71；这也不是运行了全部 2735 项注册测试的声明。

## 历史样本及其范围

[143 图旧会话冷恢复原始报告](../reports/payload-capacity/legacy143-cold-recovery-20261025.json)记录了 Windows 隔离合成 home 的真实原生运行：

- 旧 CLI 先完成 142 个 turn，第 143 图尚未消费；普通请求与手动压缩均返回 413。
- 新 CLI 冷启动后，完整 143 图压缩请求仍先返回 413；随后严格前缀中的 70 图得到新摘要，下一条成功普通请求保留并消费剩余 73 图。
- 实际原生通知为覆盖 `144/289` 个历史条目、剩余 145 个条目；这与图片数量是不同计数。全部 143 图的字节指纹、detail、顺序和原始 rollout 前缀均保留。
- 手动摘要起点为 epoch 0；后续普通响应真正完成后变成 epoch 1。进程正常退出，没有用强制清理冒充自然结束。

该报告使用 **codex-core opt0 的测试 CLI**、自有 loopback 服务和固定 30 MiB 合成边界；没有付费模型请求，也不证明 OpenRouter 的真实限制、DeepSeek 任务质量、Linux/macOS 运行、生产五个原生二进制组合或全部 runtime 等价。源码与测试修正后的最终产物仍须逐项重新验收，通过后才会更新正式安装与稳定方案。
