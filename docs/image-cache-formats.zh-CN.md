# 图片缓存格式、并发与回滚

这部分只管理模型请求的私有图片资源和本地账本。原生 Codex 继续执行线程、工具、审批、压缩、恢复与取消。迁移命令不发送推理、不访问 Files API、不读取提供方 key，也不重写原生会话或工程文件。

## 格式 3 改变了什么

每张原图按 SHA-256 取得自己的操作锁，只有同一张图的上传、核验、删除和恢复彼此等待。共享 SQLite 账本只在读取或提交本地状态时短暂加锁，远端 HTTP 不占用共享锁。所有正常操作遵守“单图锁 → 共享账本锁”，不会持共享锁等待其他图。

上传意图先持久提交，再发送上传。收到 ID 后，资源状态、回执和保护 pin 一起提交；即使返回的元数据不符，清理所需的 ID 仍先保存，再明确失败。原生请求的开始、终态和有证据的未知消费恢复，也分别按一个完整状态转换提交。事务不跨远端等待。磁盘错误、取消或进程退出不能留下半批图已推进、另一半仍是旧 phase 的账本。

这不会增加上传重试、隐式换提供方或变更原始图片字节。默认锁等待仍是 120 秒，单请求仍最多 16 个文件引用位置。未知上传不重放，未知消费不因为 PID 退出或时间经过就释放。

## 现有 home 升级到格式 3

先让这个 home 的任务、客户端和后台工作正常结束。停止 daemon 后还需要确认该 home 的 native/provider 所有者已自然退役，单独执行 daemon stop 不代表所有工作结束。不要对其他 home 或共享服务做全局终止。

保留原 home 的路径身份，使用新安装的绝对入口和原 CODEX_DEEPSEEK_HOME，在启动新 provider 之前执行：

~~~sh
codex-deepseek runtime image-cache-format --to 3
~~~

没有可核验的既有 provider 记录时，不会把缺失记录当成无人运行。未注册的外部 controller 必须自行完成整批 native/provider 的退出核验，再使用受控元数据维护 API，并单独保留退出回执；低层 API 的 complete 不等于核验了外部服务退役。

命令复用既有 provider 启动锁、kernel lease 和 PID/出生身份信息；活跃或无法证明退出的 provider/native 所有者会阻止操作。每个账本中，只要有一个 lease owner 活跃或身份未知，也会拒绝。消费状态仍未知、但 owner 已被证明退出的历史 pin 可以原样保留；迁移不会据此删除它们。

维护会先锁定并验证所有已存在的 credential scope，包括尚未建立数据库的空 scope；再非阻塞检查所有单图操作锁。忙碌、重定向路径、硬链接、未知 schema、trigger/view、非空无绑定账本或错误的 home/scope 身份都明确拒绝。受控的旧格式 1、2 和已知空账本可显式迁移，不能借迁移认领另一 home 的云资源。

原始 32 字节 scope salt 保存在私有备份中，HMAC 与 credential scope 目录不变。旧 salt 路径被原子替换为明确的长格式标记，旧格式 2 读者会在生成新 scope 前拒绝它；已有空 scope 也会建立目标身份。原 salt 从不先移走或删除，已有所有权状态上不会重新生成随机 salt。

已有 assets、pins、receipts 行保持不变，只变更格式身份。所有 scope 完成并持久核对后，根级门才变成目标格式的 ready。返回码 0 和 complete=true 才表示这次维护完成；然后按正常 runtime status、resume 和实际任务验证新入口。

新建的独立 home 在首次使用可选图片缓存时直接建立格式 3，不需要搬旧数据。

## 回滚到使用格式 2 的旧入口

先正常结束新版本在这个 home 的所有任务、客户端和 provider。仍使用**新版本的入口**运行：

~~~sh
codex-deepseek runtime image-cache-format --to 2
~~~

这会先验证并将所有现有 scope 的身份降到 2，保留升级后新增的资产、回执和未知 pin；所有数据库完成后才原子恢复原始 32 字节 salt，最后发布根级 ready 2。再切换保留的旧入口。

不能用旧数据库快照覆盖当前图片账本，不能手改版本号、删除锁、删除 salt 或清除未知 pin。回滚后的根级门阻止闲置的新格式 3 实例通过更换 key 建立新格式 scope。旧版本读者不理解新的根级 JSON，因此真实的 provider/native 退役检查仍是前置条件。

## 维护中断与诊断

任何中间写入失败都保留明确的 transition/incomplete 状态，不激活某个“部分成功”的混合组合。检查同一次输出，再用同一新入口显式重跑目标格式命令；它只恢复元数据发布，不重放上传、删除或模型请求。原有数据、salt 备份和失败证据应保留。

原版旧读者遇到格式 3 可能报告 salt 无效，或账本 ownership 不匹配。这是兼容性门，不证明提供方 key 失效。新读者遇到格式 2 或 transition 会明确要求维护；不会静默改格式或另建一个全新 scope 绕过问题。

活动图片上传期间，诊断可以看到 pending 状态。只读到 pending、发现 PID 退出、或拿到共享账本锁，都不能证明某张图的远端操作已结束。恢复必须取得对应单图操作锁；未知结果继续按原有明确的核验和清理流程处理。
